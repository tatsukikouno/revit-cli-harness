# RevitHarness

[![NuGet RevitHarness.Cli](https://img.shields.io/nuget/v/RevitHarness.Cli.svg?label=RevitHarness.Cli)](https://www.nuget.org/packages/RevitHarness.Cli/)
[![NuGet RevitHarness.Contracts](https://img.shields.io/nuget/v/RevitHarness.Contracts.svg?label=RevitHarness.Contracts)](https://www.nuget.org/packages/RevitHarness.Contracts/)

A harness add-in for Revit 2024, 2025, 2026 and 2027 that enables CLI and agent-driven test execution, command execution, and element inspection against a running Revit instance. Supports DLL hot-swapping without restarting Revit.

[日本語版 README](README.ja.md)

## Features

- **Named Pipe IPC** — Fast JSON-based communication between CLI and Revit
- **Generation loading** — DLLs are shadow-copied and loaded into fresh generations, bypassing file locks and the .NET assembly cache for seamless iterative development
- **Element Lookup** — RevitLookup-style element inspection from the CLI
- **Addin Manager UI** — A Revit ribbon button that opens a GUI to browse DLLs, scan for commands, and execute them
- **HarnessCommandBase** — Write a single class that works both from the CLI (`IHarnessCommand`) and as a Revit ribbon button (`IExternalCommand`)

## Installation

### CLI Tool

Requires the .NET 10 SDK or runtime.

```bash
dotnet tool install -g RevitHarness.Cli
```

### Deploying the Add-in

```bash
# Install: the add-in, the dialog watcher and the SKILLs (re-running overwrites cleanly)
revit-harness install --revit-version 2024   # 2024, 2025, 2026 or 2027
revit-harness install --revit-version 2024 --skills-dir D:\my-skills   # SKILLs elsewhere

# Check status
revit-harness status

# Uninstall: the add-in; the last uninstall also removes the watcher and SKILLs
revit-harness uninstall --revit-version 2024
```

> Close Revit before installing or uninstalling. Restart Revit after installation to load the add-in. Uninstall keeps `%LOCALAPPDATA%\RevitHarness\dialogs` (allowlist, logs, pending).

## CLI Commands

### ping — Health Check

```bash
revit-harness ping
```

Returns Revit version, process ID, and active document name.

### run-tests — Execute Tests

```bash
revit-harness run-tests --dll "path/to/tests.dll" --type "Company.Tests.EntryPoint" [--filter "Smoke"] [--timeout 300000]
```

Executes an `ITestEntryPoint` implementation from the specified DLL. The exit code is determined by the `passed` field in the result JSON.

### run-command — Execute a Command

```bash
revit-harness run-command --dll "path/to/command.dll" --type "Company.MyCommand" [--args '{"key":"value"}'] [--timeout 300000]
```

Executes a type implementing `IHarnessCommand` or `IExternalCommand`. An `IExternalCommand` receives a real `ExternalCommandData` (`commandData.Application` is the running `UIApplication`; `View` is the active document's active view, or `null` without a document). See `samples/SampleCommands`.

### post-command — Post a Registered Revit Command

```bash
revit-harness post-command --id "CustomCtrl_%CustomCtrl_%Add-Ins%Addin%Command"
```

Triggers a registered Revit ribbon command by its command ID.

### lookup — Element Inspection

```bash
revit-harness lookup --id 12345 [--depth 1] [--max-members 200] [--include-fields] [--include-private] [--include-static] [--filter "Name"]
```

RevitLookup-style element inspection from the CLI. Outputs property and method return values as JSON.

### shutdown — Stop the IPC Server

```bash
revit-harness shutdown
```

Stops the IPC server. Revit continues running.

### dialog-log / reload-allowlist — Automatic Dialog Handling

The add-in subscribes to `DialogBoxShowing` and `FailuresProcessing` and answers dialogs that match the allowlist (`%LOCALAPPDATA%\RevitHarness\dialogs\allowlist.json`). Every dialog and warning is logged to `dialogs_{date}.jsonl` in the same folder, tagged with `REVIT_HARNESS_TASK_ID` and the command id (`REVIT_HARNESS_COMMAND_ID`, else generated by the CLI for `run-tests` / `run-command`).

```bash
revit-harness dialog-log [--count 50]   # recent JSONL records
revit-harness reload-allowlist          # re-read and validate allowlist.json (rules are re-read on every dialog)
```

- Known rules are applied mechanically. Warnings are deleted only when a rule matches their failure id (`failure:<guid>`); errors are never resolved.
- Unknown dialogs are never decided by the harness: they become pending entries (see below).
- Revit's API exposes only the dialog id and message for task dialogs, so rules for them use `resultCode` (for example `Ok`, `Yes`, `CommandLink1`).

### Pending dialogs: how an AI driving RevitHarness resolves unknown dialogs

The harness never calls an AI itself. A dialog with no matching allowlist rule (or one matching a `noLearn` rule) is left untouched, dumped (UIA tree plus screenshot) and registered as a pending entry under `%LOCALAPPDATA%\RevitHarness\dialogs\pending\<id>.json`; the JSONL log gets `decidedBy="pending"`. The caller (an AI agent or a person) decides:

```bash
revit-harness dialog-pending [--all]      # open entries (id, title, automationId, buttons, bodySummary, screenshotPath, dumpPath, status)
revit-harness dialog-decide --id <pendingId> --button "<exact button name>" --by "<agent or model name>" [--save-rule] [--timeout 10000]
```

Check for pending dialogs whenever a command seems stuck or times out (a modal dialog blocks Revit), read `bodySummary` and the screenshot, then press one of the listed buttons. A nonexistent button is rejected. The watcher (`revit-harness dialog-watcher start`) must be running: it presses the button by UI Automation and completes the entry, which the CLI waits for (exit 0 resolved, 1 rejected/stale/failed, 2 watcher did not pick it up; the request is then withdrawn). `--by` is mandatory and lands in the log as `decidedBy="external"`, `deciderName=<by>`. A dialog that disappears before the decision is marked `stale` and cannot be decided.

`--save-rule` also writes an allowlist rule, but only for buttons known to be reversible (OK, Cancel, Close); a destructive button is pressed once and never learned, write that rule by hand if you really want it. A dialog covered by a `noLearn` rule is never saved, and neither is anything on the unsigned add-in security dialog.

**Testers**: mark the dialogs your test deliberately provokes with a rule that has `"noLearn": true`, so they are never auto-pressed or learned and always reach the caller as pending (see `samples/allowlist.sample.json`).

### Unsigned add-in security dialog

`match.addIn` is a plain string, not a pattern object, and applies only to the "Security - Unsigned Add-in" dialog: a rule with `addIn` never matches any other dialog. It is compared ordinal and case-insensitively. A value with a path separator is compared with the dll path only; any other value is compared with the add-in name and the dll file name, so an add-in cannot impersonate a path through its self-declared name. Without `*` it must match exactly. A trailing `*` (for example `Contoso.*`) makes it a prefix match; any other `*` is literal and there is no regex. A lone `*` matches every unsigned add-in, so it loads unknown unsigned add-ins too. For the security dialog only a rule with an `addIn` condition can answer, so known add-ins get the configured button (for example "Load Once") and every other add-in becomes pending. "Always Load" and "Do Not Load" are never learned. Rules may also use `match.automationId` and `match.buttons` (exact button-name set) next to `title` and `text`. A text pattern needs a non-empty `value`; an omitted `mode` means `equals`. A matching `noLearn` rule always wins over earlier rules, and a matching rule whose action does not apply to the dialog leaves it pending. See `samples/allowlist.sample.json`.

## Dialog Watcher (FlaUI)

`src/RevitHarness.DialogWatcher` is an on-demand exe (net10.0-windows, needs the .NET 10 Desktop Runtime, no Revit dependency) that watches Revit.exe top-level windows and Windows error reporting dialogs (WerFault) through UI Automation (WindowOpened event plus a 300 ms poll). Known dialogs are answered from the allowlist (`%LOCALAPPDATA%\RevitHarness\dialogs\allowlist.json`) by pressing the button with the UIA Invoke pattern (never the real mouse). Unknown dialogs get a UIA tree dump in `dialogs\dumps\`, a screenshot in `dialogs\screenshots\` and a JSONL log record plus a pending entry; nothing is pressed. `install` and `uninstall` refuse to run while Revit.exe is running (close Revit first), and `install`, `uninstall` and `dialog-watcher start|stop` take a cross-process lock and fail with a message when another one is running. `dialog-watcher start` fails with a message naming the .NET Desktop Runtime to install when it is missing.

```bash
dotnet build src/RevitHarness.DialogWatcher -c Debug -p:Platform=x64   # only needed when building from source
revit-harness dialog-watcher start     # idempotent: no second instance; prints pid and log location
revit-harness dialog-watcher status    # exit 1 when not running
revit-harness dialog-watcher stop
RevitHarness.DialogWatcher.exe --once --dry-run              # one pass, log only
RevitHarness.DialogWatcher.exe --selftest                    # fake WinForms dialog, needs an interactive desktop
```

`revit-harness install` copies the watcher to `%LOCALAPPDATA%\RevitHarness\watcher\`. It is never started automatically and never resident by itself: start it before launching Revit and stop it when done (the `revit-harness-dialogs` SKILL tells an AI agent to do exactly that). Install stops a running watcher before replacing it.

Exe options: `--once`, `--dry-run`, `--pid <revit pid>`. The allowlist, pending entries and logs always live under `%LOCALAPPDATA%\RevitHarness\dialogs`. Stop with Ctrl+C or by creating `dialogs\watcher.stop`. A session-local named mutex (`Local\`) prevents a second watcher per Windows session; the pending-store and log mutexes are session-local too, so run the watcher, add-in and CLI in the same session.

## Target add-in hot reload

Reload a resident `IExternalApplication` and its own helper DLLs without restarting Revit.
Build for Revit 2024 (net48), 2025/2026 (net8.0-windows), or 2027 (net10.0-windows),
keep helpers beside the target DLL, and use `Private=False` for Revit API references.
Load the target through the harness only; remove its own `.addin` to avoid double loading.

```bash
revit-harness reload --dll "C:\path\SampleTarget.dll" --type SampleTarget.App [--timeout <ms>]
revit-harness target-status
revit-harness unload [--timeout <ms>]
```

Reload runs old `OnShutdown`, disposes the old generation, shadow-copies, and runs new
`OnStartup`. Shutdown exceptions become warnings and reload continues. Startup exceptions
fail the request (`ok=false`) and leave the target `Unloaded`. `target-status` reports the
current generation, path/type, load time, runtime, working set, generation counts, old live
ALCs (null on net48), and ribbon bindings. `status` remains the installation status command.

In target `OnStartup`, register buttons with the Contracts helper:

```csharp
TargetRibbon.AddPushButton(panel, "Hello", "Hello", typeof(HelloCommand).FullName!);
```

A button with the same name on the same panel reuses the existing button, updates its text, and rebinds it to
the current generation. Revit cannot remove ribbon items: buttons point to permanent
`TargetSlot0`–`TargetSlot7` command stubs in `RevitHarness.Addin.dll`. At most eight distinct
buttons are supported; after unload the buttons remain but cannot execute target code.

The harness `.addin` serves as the thin loader. Each successful reload saves the target DLL
path and type to `%LOCALAPPDATA%\RevitHarness\target.json`. Harness startup restores that
target so its ribbon exists immediately; restoration failure is non-fatal. `unload` deletes
the file and stops the target.

The target's `OnShutdown` must unregister updaters, unsubscribe events, dispose
`ExternalEvent` instances and timers, and stop background work. On net8/net10 each reload
uses a new collectible AssemblyLoadContext; references left behind can prevent release
(check `previousReleased`, `released`, and warnings). On net48 each reload byte-loads a new
generation; old generations stay in memory until Revit exits. Native DLLs are unsupported.
Byte-loaded assemblies have an empty `Assembly.Location`; avoid using it to locate assets.
Register `IUpdater`s with `application.ActiveAddInId` (the harness's id while it hosts the
target); Revit rejects any other owner. On net48 the .NET Framework binder reuses any loaded
assembly with the same simple name, so the harness renames the target's own helper DLLs per
generation (Mono.Cecil, names only) so a rebuilt helper is really used. Values a command
serializes through the host's Newtonsoft.Json with its own types (for example anonymous
objects) stay in that library's caches and keep a net8+ generation from being released.
See [SampleTarget](samples/SampleTarget/README.md) for build commands and a probe of
startup/shutdown, helper DLL updates, events, updaters, and ribbon rebinding.

## Addin Manager UI

After launching Revit, access it from the **RevitHarness** ribbon tab → **Addin Manager** button.

1. **Browse** to select a DLL
2. **Scan** to list types implementing `IHarnessCommand` / `IExternalCommand`
3. Select a type and click **Execute**
4. Results are displayed in the text area at the bottom

## Implementing Tests and Commands

### Contracts Package

```bash
dotnet add package RevitHarness.Contracts
```

### ITestEntryPoint — For Tests

```csharp
using RevitHarness.Contracts;

public class MyTestEntryPoint : ITestEntryPoint
{
    public string Run(UIApplication uiapp, IDictionary<string, object> args)
    {
        var doc = uiapp.ActiveUIDocument.Document;
        // Test logic
        return JsonConvert.SerializeObject(new { passed = true, summary = "All tests passed" });
    }
}
```

### IHarnessCommand — For Commands (CLI Only)

```csharp
using RevitHarness.Contracts;

public class MyCommand : IHarnessCommand
{
    public string Execute(UIApplication uiapp, IDictionary<string, object> args)
    {
        // Command logic
        return JsonConvert.SerializeObject(new { result = "done" });
    }
}
```

### HarnessCommandBase — CLI + Ribbon Dual Use

Use this when you want a single class that can be executed both from the CLI (`revit-harness run-command`) and as a Revit ribbon button (`IExternalCommand`).

```csharp
using RevitHarness.Contracts;

[Transaction(TransactionMode.Manual)]
public class MyDualCommand : HarnessCommandBase
{
    public override string Execute(UIApplication uiapp, IDictionary<string, object> args)
    {
        var doc = uiapp.ActiveUIDocument.Document;
        // Works from both CLI and ribbon
        return JsonConvert.SerializeObject(new { result = "done" });
    }
}
```

## IPC Protocol

JSON messages over Named Pipe `\\.\pipe\RevitHarness2024` with length-prefix framing (int32 LE).

| Operation | Description |
|-----------|-------------|
| `ping` | Health check |
| `runTests` | Execute `ITestEntryPoint` |
| `runCommand` | Execute `IHarnessCommand` / `IExternalCommand` |
| `postCommand` | Post a registered Revit command |
| `reload` | Replace the target IExternalApplication generation |
| `unload` | Stop and dispose the target generation |
| `targetStatus` | Target state, memory, generations, ribbon slots |
| `lookupElement` | Element inspection |
| `shutdown` | Stop the IPC server |
